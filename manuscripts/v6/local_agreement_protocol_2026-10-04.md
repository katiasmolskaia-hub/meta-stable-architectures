# Контроль согласования смены связей: протокол малого стенда

4 октября 2026, до расчёта. Цель — проверить упрощение, которое скрывал прежний мгновенный обмен AB, CD → AC, BD. Это **отдельный стенд одной договорённости четырёх живых участников**, не новая серия снабжения 960 узлов и не физический рой.

## Какие контроли нужны

1. Без смены связей: старые договорённости сохраняются. Нулевая перестройка не считается успешным восстановлением.
2. Идеальный атомарный обмен: все четыре меняются мгновенно, сообщения не требуются. Это прежнее идеализированное допущение, не честный конкурент по цене связи.
3. Одна команда без подтверждения: инициатор меняется сам и посылает остальным по одной команде. Отрицательный контроль показывает цену потери сообщения.
4. Обычное согласование с подтверждениями без повторов: подготовка/голоса, затем окончательное решение/подтверждения.
5. То же согласование с повторами недостающих сообщений. Это упрощённая учебная реализация стандартной идеи двухфазного подтверждения, **не новый авторский алгоритм и не заявка на лучший способ управления роем**.

Инициатор — один из четырёх участников, не наблюдатель всей сети. У каждого только своё состояние заменяемой связи. Все четыре согласны на подготовку, если сообщение дошло; конкуренция за узел пока отсутствует. Старые записи сохраняются при подготовке. Решение COMMIT принимается только после всех голосов YES; до решения инициатор может выбрать ABORT после 16 тактов. После окончательного решения оно не меняется. Подготовленный участник не отменяет обещание сам по таймеру: другой узел уже мог получить COMMIT.

Повтор через 4 такта, горизонт 80, каждому участнику разрешено не больше 24 отправок, включая ответы. Дубликат может вызвать ответ, но не повторную смену записи и не повторную плату. Плата здесь только счётчик: один заранее назначенный помощник отмечает её при своём первом переключении. Ресурсная динамика не моделируется.

## Сценарии и измерения

По 200 seed 14000–14199; пять вариантов и шесть профилей, 6000 прогонов. Одинаковые параметры канала и функция его состояния для одинаковых seed, времени и направленной пары узлов; одновременные сообщения на одном канале разделяют судьбу. Это явно заданная корреляция, не независимые потери каждого пакета.

Профили: задержки 1–4 такта без потерь; потери 10%; потери 30%; потери 10% с вероятностью дубликата 30% и дополнительной задержкой 1–8; отсутствие связи с участником №3 до такта 24; постоянная потеря сообщений об окончательном решении участнику №3. Последний профиль — намеренная проверка предела, не типичная модель радиоканала.

Измеряем отдельно: все ли перешли к новой связи; осталась ли частичная смена; сколько подготовленных обещаний зависло; сколько тактов записи соседей расходились; сколько «узло-тактов» заменяемое ребро не имело взаимного подтверждения; число отправок, потерь, повторных доставок, исчерпаний бюджета; время физического завершения и получения всех подтверждений. В полной сети у узла остаются другие соседи: отсутствие взаимного **заменяемого** ребра не тождественно изоляции всего узла.

Ноль противоречащих решений COMMIT/ABORT **не означает** одновременного физического переключения всех концов связи. Временную асимметрию записей не прячем за общей матрицей смежности.

## Ограничения и источники

Инициатор не отказывает, решение сохраняется, один обмен не конкурирует с другим, энергия и поток ресурса отсутствуют, положительный ABORT считается согласованным отказом от операции, а не восстановлением. При постоянной потере окончательного решения ожидается блокирование. Такие ограничения стандартного двухфазного подтверждения описаны у [Gray и Lamport, Consensus on Transaction Commit](https://www.microsoft.com/en-us/research/publication/consensus-on-transaction-commit/).

Реальные системы не имеют единственного универсального способа «восстановить связь»: например, [Kilobot](https://users.cs.northwestern.edu/~mrubenst/ICRA12.pdf) использует локальную инфракрасную коммуникацию, а [Crazyswarm](https://crazyswarm.readthedocs.io/en/latest/index.html) — радиообмен с широковещательными передачами там, где это возможно. Наши программно выбираемые каналы передачи ресурса не равны непосредственно этим физическим каналам.

Запуск: `python -m unittest discover -s simulations -p test_local_agreement.py`, затем `python simulations/experiment_local_agreement.py`. Следующий переход к полной сети допустим только с явным учётом частичного переключения и блокировок; результат малого стенда не переносится автоматически на снабжение.
